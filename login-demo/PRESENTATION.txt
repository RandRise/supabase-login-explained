STUDENT PORTAL — ABOUT 5–6 MINUTES

BEFORE SCREEN SHARING
Open the portal and /swagger in two tabs on the same host/port.
Sign in as Bob once, submit different answers, then sign out. This gives Bob
a real result for the ownership test. Keep both invented passwords nearby.
Swagger starts without a bearer token. No speaking notes are built into the app.

1. GUEST — 30 SECONDS
Show the quiz questions. Click View my result while signed out.
Open Last data request: real HTTP 401.

Say: "The questions are public. Results are private. The server needs a valid
student token before it will return a result."

2. ALICE LOGS IN AND TAKES THE QUIZ — 60 SECONDS
Sign in as Alice. Choose answers and click Submit answers.
Correct choices: browser localStorage; authenticated user; decoding is not
verification. The request sends answer numbers, not a score.

Say: "The password goes over HTTPS to Supabase Auth. Supabase checks it and
returns a session. Later requests use an access token instead of resending
the password. The database calculates this score and assigns it to Alice."

Explain, rather than claim to observe: Supabase stores salted bcrypt password
hashes. Our page clears its password field; a browser password manager is
separate and may offer to save the password.

3. RELOAD AND INSPECT STORAGE — 45 SECONDS
Reload the portal. Alice remains signed in and her result is fetched again.
In Chrome DevTools: Application > Local Storage > this site's origin.
Find team3-student-session-v1: access_token, refresh_token, user and scope.
Do not copy the entire storage record into slides or Discord.

Say: "The page remembers the session in this browser. The access token is
sent again, and the server checks it again. This app requires another login
when the access token expires; automatic refresh isn't part of this demo."

4. SWAGGER: THE SAME CALL WITH AND WITHOUT A TOKEN — 60 SECONDS
Switch to Swagger. Click Use portal session.
Expand POST /rest/v1/rpc/team3_get_result > Try it out > Execute.
Keep {"p_student_id": null}. See HTTP 200 with Alice's actual result.
Click Remove bearer token, then Execute again. See HTTP 401.
Click Use portal session again.

Expand Decoded token claims. Point out sub, email, role and expires_at.
Say: "This reads the token's claims locally. Readable doesn't mean trusted.
Supabase verifies the signature and validity when the request arrives."

5. ALICE CANNOT BECOME BOB — 45 SECONDS
In Swagger, execute GET /rest/v1/team3_quiz_students and copy Bob's invented
UUID. In the result request, replace null with Bob's quoted UUID and Execute.
See HTTP 403. Restore null afterwards.

Say: "Alice has a valid token, but it represents Alice. Being logged in isn't
permission to read every student's result."

Optional deeper check: query /rest/v1/team3_quiz_attempts with
student_id = eq.BOBS_UUID. Alice sees HTTP 200 with [] because RLS filters the
rows. Bob's baseline must exist before describing this as an ownership check.

6. A COPIED TOKEN — 45 SECONDS
Keep Alice's bearer attached in Swagger. Sign out of the portal.
Return to Swagger without reloading and execute the own-result request.
A still-valid copied bearer can return Alice's result. It can also submit
another attempt as Alice through the quiz endpoint.

Say: "A stolen bearer token can act as its owner while it remains valid.
Logging out clears our local session and revokes its refresh capability,
but a previously issued access token can remain usable until it expires.
It does not reveal Alice's password, make us Bob, or bypass database policies."

Remove the bearer and clear responses when finished.

HANDOFF
Google sign-in is the teammate's section. Our app doesn't perform live OAuth.
The provider-side password hashing is explained from official documentation,
not observed by reading password hashes. No naturally expired token was timed
during validation. Do not label an arbitrary 404 or network failure as an
authentication success.
