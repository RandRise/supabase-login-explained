Say: "This page restores its saved session from localStorage. It sends the
token again and the server still checks access. It does not save the password."

2:00 — FIND AND DECODE THE TOKEN
Chrome DevTools > Application > Local Storage > this site.
Select team3-supabase-session-v1. Identify access_token, refresh_token and user.
In DevTools Console, run these lines (no external JWT-decoding website needed):

const demoSession = JSON.parse(localStorage.getItem('team3-supabase-session-v1'));
const demoCore = await import('/core.mjs');
const demoClaims = demoCore.decode(demoSession.access_token).payload;
console.table({ user: demoClaims.sub, email: demoClaims.email, role: demoClaims.role,
  expires: new Date(demoClaims.exp * 1000).toISOString() });

Say: "These are readable claims, not the password. Decoding does not verify
the signature. Supabase verifies the token before the request reaches RLS."
Keep the full credential out of shared notes/recordings.

PASSWORD EXPLANATION (DOCUMENTED, NOT A HASH-INSPECTION DEMO)
The browser sends email/password directly to Supabase over HTTPS.
Supabase stores salted bcrypt hashes and checks the supplied password.
Hashing is not encryption that can be reversed to recover the password.
The Node server here only serves files; it never processes login credentials.

DO NOT OVERCLAIM
This is not end-to-end encrypted messaging. A project administrator can read
the database. The copied token may also allow other account actions exposed
by the provider; the limits above concern this demo and the original password.
We did not test natural expiry by waiting. Google OAuth is not implemented here.
